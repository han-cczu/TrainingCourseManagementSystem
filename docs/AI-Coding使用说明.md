# AI Coding 使用说明

本项目的代码、测试、文档和交付物，基本都是在 AI 编码助手的协助下完成的。本文如实记录：用了什么工具、人和 AI 怎么分工、关键决策由谁做出、AI 出过哪些错以及如何纠正，以及我们怎样保证 AI 产出的质量。

## 1. 工具

| 工具 | 用途 |
|---|---|
| **Claude Code**（命令行，Windows） | 主要的 AI 编码助手：读题、出方案、写设计、编码、跑测试、操作 Git/GitHub、写文档 |
| 模型 **Claude Opus 5.5**（`claude-opus-5-5`） | Claude Code 使用的模型 |
| GitHub CLI（`gh`） | AI 用它创建仓库、提交 PR、查看 CI 结果、合并 PR |
| Docker / Testcontainers / Playwright | AI 用它们在本地验证自己的产出：启动全栈、跑集成测试、驱动浏览器自测并截图 |

AI 在开发者本机的终端里执行命令（构建、测试、Git 操作等）。会产生外部影响的操作，比如创建公开仓库、合并 PR，都是先征得同意再做。

## 2. 协作流程

```
读题 → AI 给出实现方案并列出待决策项 → 人逐项决策
     → 技术设计（docs/技术设计.md）→ 按 PR 拆分实现计划（docs/实现计划/）→ 把约定写进 CLAUDE.md
     → 每个 PR：AI 编码 → 自动化测试 → UI 自测脚本 → 截图复核 → 更新文档
                → 提交 PR（附测试结果、截图、AI 使用情况）→ CI → 人评审并合并
```

- **先出方案，再写代码**：读完题目后，AI 没有直接动手，而是先给出完整方案，并把需要人拍板的问题单独列出来（见第 3 节）。
- **文档是 AI 的「记忆」**：设计决策写在技术设计里，每个 PR 的任务和验收标准写在实现计划里，编码和测试约定写在 `CLAUDE.md` 里。开新的会话窗口时，AI 会自动读取这些文件，从而保持一致。
- **小步提交、逐个评审**：共 6 个 PR，每个 PR 都是「后端 + 对应前端页面」的完整功能，合并后可以直接在页面上验证。

## 3. 决策：人来定，AI 提供建议

| 决策点 | AI 的建议 | 人的选择 |
|---|---|---|
| 身份认证 | 模拟身份切换（省时间） | **做真实登录**（JWT） |
| 账号来源 | 员工自助注册 | **自助注册和管理员建号都要** |
| 谁来标记「学习完成」 | 管理员标记 | **员工本人和管理员都可以** |
| ORM | JPA（并说明了理由和 MyBatis-Plus 的优势） | 询问理由后，**选择 MyBatis-Plus**（与团队习惯一致） |
| 时间规则 | 提出可选项 | **加上「开课后不能报名或取消」** |
| 是否考虑上线 | 最初只设计到能在 K8s 上运行 | 人提出「最后要上线到服务器」，AI 据此补充了部署清单和部署手册 |
| 部署环境 | 列出需要确认的问题（云厂商、架构、镜像仓库、域名） | 火山云单机 K8s、amd64、MySQL 部署在集群内、不用域名；之后又决定**先在本地完成全部功能，上线后置** |
| 仓库 | — | 公开仓库，名称 TrainingCourseManagementSystem |
| PR 拆分方式 | 建议从「前端集中在一个 PR」改为按功能纵向切分 | 同意 |

AI 也会主动查证事实，而不是凭记忆下结论：
- 选版本时查询了 Maven Central 和 endoflife.date，发现 Spring Boot 3.5 的开源支持已于 2026-06 结束，因此选择 4.1.2。
- 发现 TypeScript 7 是全新的原生编译器，与 vue-tsc 的兼容风险较大，因此暂用 6.0。
- 通过 APNIC 查询服务器 IP，确认服务器在火山引擎。
- 查询了火山引擎和阿里云镜像仓库的收费情况。

## 4. 分工

| 由 AI 完成 | 由人完成 |
|---|---|
| 项目骨架、全部前后端代码、数据库迁移 | 关键决策（第 3 节） |
| 82 个后端测试、25 项 UI 自测脚本 | 评审每个 PR，决定是否合并（部分 PR 由人亲自在网页上合并） |
| Dockerfile、docker-compose、K8s 清单、部署脚本 | 提供服务器环境信息；安装本机工具（JDK、gh）并完成登录 |
| 技术设计、实现计划、部署手册、自测说明、本文档 | 发现方向性问题，比如提出「要上线」 |
| 创建仓库、提交 PR、编写 PR 描述、查看 CI 结果 | |

## 5. 关键提示词（人的原话）

AI 的产出由这些简短指令推动，细节都由 AI 在方案和文档里展开，再由人确认：

1. 「阅读文件夹下的题目.md 帮我制定实现方案」（题目原文属于内部资料，未放入公开仓库；需求范围见技术设计 §1.2）
2. 「1.做真正的登录好一点吧 2两种都支持 3。为什推荐JPA，4加「课程开始后不能报名或取消」这类规则」
3. 「用MyBatis-Plus吧」，「员工自己注册和管理员都要」
4. 「最后这个项目需要上线到服务器的，这些也考虑了吗？」
5. 「先在本地搞好整个项目，上线的事情后面再说」
6. 「需要把几个pr都写上独立的实现文档吧？」
7. 「开始吧」，「继续接下来的开发吧」，「帮我合并，然后接着做」

## 6. AI 出过的错与纠正（真实记录）

AI 并非一次就能写对。下面这些问题大多由 AI 通过测试、复现或截图复核自己发现并修复；其中第 3 条是破坏性错误，AI 发现后主动向人报告。

| # | 问题 | 怎么发现的 | 如何处理 |
|---|---|---|---|
| 1 | 建表脚本里的 `TINYINT(1)` 触发了 MySQL 8 的废弃警告 | 第一次启动时检查日志 | Flyway 迁移脚本一旦提交就不能再改，所以趁还没提交时改成 `BOOLEAN`，重建本地数据库后确认警告消失 |
| 2 | 测试镜像时，在只读文件系统下前端没有启动成功，一开始误以为是镜像本身的问题 | 进入容器排查 | 实际原因是 Docker `--tmpfs` 默认挂载的目录权限不够写入；改用与 K8s emptyDir 相同的 0777 权限后验证通过，镜像没有问题 |
| 3 | **误删了用户一个无关的容器**：清理测试容器时用了 `docker container prune`，范围过大，删掉了一个已停止的 sillytavern 容器 | AI 事后用 `docker events` 自查发现 | 立即如实告知，并核实了影响范围（镜像和数据卷都还在）。用户确认这个容器不需要了。之后只按名称删除 AI 自己创建的资源 |
| 4 | UI 自测里 `waitForURL('**/courses')` 也会匹配上 `/login?redirect=/courses`，导致一项自测误报失败 | 单独写脚本复现 | 确认应用本身没有问题，把等待条件改为按路径精确匹配，并封装进 `lib.mjs` |
| 5 | 测试里把时钟拨快超过 8 小时后，之前签发的 JWT 已经过期，3 个测试返回 401 | 测试失败 | 拨动时钟后重新签发 token，并把这条写进 `CLAUDE.md` 的测试约定，后续的 PR 没有再犯 |
| 6 | **真实缺陷**：本地 compose 里后端没有健康检查，`up --wait` 返回时 Spring Boot 还没启动完 | UI 自测在刚启动后立刻运行时失败 | 给后端加上 readiness 健康检查，前端改为等后端健康后再启动 |
| 7 | e2e 里执行 SQL 的辅助函数没有指定 utf8mb4，同时还丢弃了错误输出，导致含中文的查询条件匹配不到任何行，问题却没有暴露出来 | 自测中拿到的课程 ID 是空的 | SQL 改为通过 stdin 传入，指定字符集，出错时直接抛异常 |
| 8 | e2e 在列表接口还没返回时就开始数卡片 | 自测失败 | 等接口响应返回、加载遮罩消失后再断言 |
| 9 | `StatsIT` 的预期值是手算的，4+2+3 被算成了 7 | 测试失败 | 先核对 SQL 的统计口径，确认统计代码是对的，再修正测试里的预期值 |
| 10 | Element Plus 标签的入场动画，导致截图里的标签看不见；之后用 sed 批量修复时还漏了一处 | AI 复核截图 | 统一关闭标签的过渡动画；PR6 再次复核截图时发现漏掉的那一处，补上 |
| 11 | 改成按需引入后，组件 CSS 的加载顺序变了，导致导航栏边框的样式覆盖失效 | 复核截图，再用浏览器读取计算后的样式确认 | 提高选择器优先级，并把这个注意事项写进技术设计 §8.2 |

另外，有些问题是 AI 在编码时就预先避免的：
- MyBatis-Plus 的 `updateById` 默认会跳过值为 null 的字段，所以「改为不限人数」默认不会生效。编码时就为可以置空的字段设置了 `FieldStrategy.ALWAYS`，并写了测试覆盖。
- 编辑课程时，提交的时间如果带小数秒，会被误判为「改了时间」。服务端统一截断到秒，并写了测试覆盖。

## 7. 如何保证 AI 产出的质量

1. **测试是硬门槛**：后端 82 个测试用真实的 MySQL 跑（Testcontainers），其中并发测试每个场景重复跑 3 次；每个 PR 都必须通过 CI 才能合并。
2. **UI 自测由 AI 自己执行**：每份 PR 实现文档里的「自测清单」都写成了 Playwright 脚本，AI 在真实页面上逐项操作并截图，而不是只说一句「我测过了」。
3. **截图复核**：AI 会亲自查看截图，以此发现功能测试发现不了的视觉问题（第 6 节第 10、11 条）。
4. **测试失败时先判断原因**：区分是代码有问题，还是测试本身写错了（第 6 节第 4、5、9 条都是测试或脚本的问题，应用代码没有错），避免「改代码去迎合错误的测试」。
5. **文档和代码同步**：每个 PR 都把新确定的细节写回技术设计；PR 描述里写明对应的设计章节、测试明细，以及本次 AI 出过哪些错。
6. **人做最终把关**：关键决策和合并都由人完成。

## 9. 经验与建议

- **让 AI 先出方案，人来做决策**：AI 适合把选项和利弊摆清楚，而像「做真实登录」「要上线」这类方向性判断，应该由人来做。
- **把约定写进文件，不要只停留在对话里**：`CLAUDE.md` 加上设计文档，能让 AI 跨会话保持一致；AI 自己踩过的坑（比如 token 过期）也要写进去。
- **要求 AI 查证，不要凭记忆**：版本、维护周期、价格这类信息变化很快。
- **测试会写错，AI 算数也会算错**：测试失败时，先判断是代码错了还是测试错了。
- **对破坏性操作要限定范围**：批量清理类命令（prune、`rm -rf`）应该只作用于明确列出的目标；出了错要如实报告。
- **端到端验证不可省**：本项目里有几个问题（compose 健康检查缺失、CSS 加载顺序），单元测试和集成测试都发现不了，只有在真实环境里跑一遍 UI 自测、看一眼截图才能发现。
