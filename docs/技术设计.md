# 培训课程管理系统 · 技术设计

> 版本 v1.0 · 2026-11-04

## 1. 概述

### 1.1 背景与目标
公司内部需要一个简单的培训课程系统：员工可以查看课程、报名，并查看自己的培训情况；管理员可以维护课程、查看报名人员并做统计。

### 1.2 需求范围

| # | 需求 | 实现位置 |
|---|---|---|
| 1 | 创建课程 | §7.3 `POST /api/courses` |
| 2 | 编辑课程 | §7.3 `PUT /api/courses/{id}` |
| 3 | 查看课程列表 | §7.3 `GET /api/courses` |
| 4 | 用户报名课程 | §7.4 `POST /api/courses/{id}/enrollments` |
| 5 | 用户取消报名 | §7.4 `DELETE /api/courses/{id}/enrollments/me` |
| 6 | 查看课程已报名人员 | §7.4 `GET /api/courses/{id}/enrollments` |
| 7 | 标记课程学习完成 | §7.4 员工自己标记 + 管理员标记 |
| 8 | 查看我的报名 | §7.4 `GET /api/me/enrollments` |
| 9 | 基础统计 | §7.5 |
| 扩展 | 课程容量限制 | §5.2、§6 |
| 增加 | 真实登录（注册 + 管理员建号） | §4 |
| 增加 | 时间规则（开课后不可报名/取消） | §5.3 |

### 1.3 不做的事（明确排除）
- 不引入 Redis / MQ / 微服务：容量并发通过 MySQL 行锁解决（§6）。
- 不做 refresh token 和找回密码（没有邮件服务），由管理员重置密码代替。登录限流在 nginx 层实现（§9.4），后端不做。
- 不做课程删除、候补队列、通知、用户角色变更。

**为什么用 MyBatis-Plus：** 和团队现有技术栈保持一致；SQL 完全透明，不会遇到 JPA 的 N+1、懒加载问题；统计这类聚合 SQL 直接写更清楚。
**MyBatis-Plus 使用约定：**
- 单表增改查用 `BaseMapper` / `LambdaQueryWrapper`；有连表或聚合的查询写在 `resources/mapper/*.xml` 里，返回 DTO。
- 业务代码里不用 `wrapper.last()` 拼 SQL，行锁写成 Mapper 的专用方法 `selectByIdForUpdate`。
- 分页用 `PaginationInnerInterceptor`。从 3.5.9 起它被拆到单独的 `mybatis-plus-jsqlparser` 依赖里，需要额外引入。
- `created_at` / `updated_at` 由 `MetaObjectHandler` 自动填充，时间统一从 `Clock` 取（§5.4）。

## 4. 认证与权限

### 4.1 角色

| 角色 | 能做什么 |
|---|---|
| EMPLOYEE | 浏览课程、报名/取消、自己标记完成、查看我的报名和个人统计、修改自己的密码 |
| ADMIN | 以上全部 + 创建/编辑课程、查看报名人员、给任何人标记完成、全局统计、用户管理 |

### 4.2 账号来源（两种都支持）
1. **员工自己注册**：`POST /api/auth/register`，角色固定为 EMPLOYEE，注册时不能自己指定角色。
2. **管理员建号**：在用户管理页创建账号，可以选择角色（EMPLOYEE / ADMIN）。管理员还能停用/启用账号、重置密码。
3. **初始管理员**：应用启动时，如果数据库里没有 ADMIN，就用环境变量 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 创建一个。K8s 里这两个值来自 Secret，代码和迁移脚本里都不写默认密码。多个副本同时启动时，可能都去创建管理员，没抢到的那个会触发唯一键冲突，捕获后忽略即可。

本地开发时，`application.yml` 里提供了默认值：管理员账号 `admin` / `Admin12345`，以及一个以 `dev-only-` 开头的 JWT 密钥。在 prod profile 下，如果仍在使用这些默认值，`ProdSafetyCheck` 会**直接拒绝启动**，防止带着默认密码上线。

### 4.3 校验规则
- 用户名：3–32 位，只能是字母、数字、下划线，全局唯一，且**不区分大小写**：`ZhangSan` 和 `zhangsan` 视为同一个用户名，因为数据库排序规则 `utf8mb4_0900_ai_ci` 本身不区分大小写。
- 密码：8–64 位，至少包含字母和数字；用 BCrypt 加密存储。
- 登录失败一律返回「用户名或密码错误」：用户不存在、密码错误、账号已停用这三种情况都一样，防止别人借此探测哪些用户名存在。用户不存在时，后端也会做一次 BCrypt 比对，让响应时间和「密码错误」时一致，不能通过响应快慢判断。
- 修改密码时原密码错误，返回 **400** `VALIDATION_ERROR`（`details.fields.oldPassword`），而不是 401。因为前端收到 401 会当作登录失效，直接跳转到登录页。

### 4.4 JWT
- 用 HS256 签名，密钥来自环境变量 `JWT_SECRET`（至少 32 字节），有效期 8 小时，不做刷新。
- Claims：`sub` = 用户 ID，`username`，`role`。其中 `role` 只给前端展示用。
- **每次请求都会按用户 ID 查一次用户**（主键查询，开销可以忽略）：用户不存在或已停用就返回 401；角色以数据库为准。这样停用账号能马上生效，不用等 token 过期。
- 签发用 `NimbusJwtEncoder`，校验用 `NimbusJwtDecoder.withSecretKey`，都通过 Spring Security 的 OAuth2 Resource Server 接入，不手写过滤器。
- 管理员接口在方法上加 `@PreAuthorize("hasRole('ADMIN')")`。
- 管理员不能停用自己，防止系统里没人能登录管理。

## 5. 数据模型与业务规则

### 5.1 表结构（`V1__init.sql`）

```sql
CREATE TABLE sys_user (
  id            BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
  username      VARCHAR(32)  NOT NULL,
  password_hash VARCHAR(100) NOT NULL,
  real_name     VARCHAR(32)  NOT NULL,
  department    VARCHAR(64)  NULL,
  role          VARCHAR(16)  NOT NULL,              -- ADMIN / EMPLOYEE
  enabled       TINYINT(1)   NOT NULL DEFAULT 1,
  created_at    DATETIME     NOT NULL,
  updated_at    DATETIME     NOT NULL,
  UNIQUE KEY uk_user_username (username)
);

CREATE TABLE course (
  id             BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
  title          VARCHAR(100) NOT NULL,
  description    TEXT         NULL,
  instructor     VARCHAR(32)  NOT NULL,
  location       VARCHAR(100) NULL,
  start_time     DATETIME     NOT NULL,
  end_time       DATETIME     NOT NULL,
  capacity       INT          NULL,                 -- NULL = 不限人数（扩展任务）
  enrolled_count INT          NOT NULL DEFAULT 0,   -- 冗余计数 = ENROLLED + COMPLETED 的人数
  created_by     BIGINT       NOT NULL,
  created_at     DATETIME     NOT NULL,
  updated_at     DATETIME     NOT NULL,
  KEY idx_course_start_time (start_time),
  CONSTRAINT fk_course_creator FOREIGN KEY (created_by) REFERENCES sys_user (id),
  CONSTRAINT chk_course_time     CHECK (end_time > start_time),
  CONSTRAINT chk_course_capacity CHECK (capacity IS NULL OR capacity > 0),
  CONSTRAINT chk_course_count    CHECK (enrolled_count >= 0)
);

CREATE TABLE enrollment (
  id           BIGINT      NOT NULL AUTO_INCREMENT PRIMARY KEY,
  course_id    BIGINT      NOT NULL,
  user_id      BIGINT      NOT NULL,
  status       VARCHAR(16) NOT NULL,                -- ENROLLED / CANCELLED / COMPLETED
  enrolled_at  DATETIME    NOT NULL,
  cancelled_at DATETIME    NULL,
  completed_at DATETIME    NULL,
  completed_by BIGINT      NULL,                    -- 等于 user_id 表示本人确认，否则是管理员确认
  created_at   DATETIME    NOT NULL,
  updated_at   DATETIME    NOT NULL,
  UNIQUE KEY uk_enrollment_course_user (course_id, user_id),
  KEY idx_enrollment_user_status   (user_id, status),
  KEY idx_enrollment_course_status (course_id, status),
  CONSTRAINT fk_enrollment_course FOREIGN KEY (course_id) REFERENCES course (id),
  CONSTRAINT fk_enrollment_user   FOREIGN KEY (user_id)   REFERENCES sys_user (id)
);
```

设计要点：
- **多对多**：课程和用户之间通过 `enrollment` 关联表连接。关联表本身有状态和时间字段，所以建成独立的实体。
- **同一个人在同一门课只有一行记录**：取消后再报名时复用这一行（状态改回 ENROLLED，刷新 `enrolled_at`，清空 `cancelled_at`）。唯一索引用来最终防止重复报名。
- **用户表叫 `sys_user`**，不叫 `user`，以免和 MySQL 关键字、系统库的 `mysql.user` 混淆。
- 状态字段用 `VARCHAR` 加 Java 枚举，不用 MySQL 的 `ENUM` 类型，以后加状态不用改表。
- 加了外键但不级联：系统没有删除操作，外键只起完整性兜底作用。

### 5.2 报名状态机

```
           报名（开课前、有名额）
  (无记录) ─────────────────────▶ ENROLLED ──标记完成（开课后，本人或管理员）──▶ COMPLETED（终态）
                                   │   ▲
                       取消（开课前）│   │ 重新报名（开课前、有名额）
                                   ▼   │
                                  CANCELLED
```

| 操作 | 前提状态 | 时间条件 | 名额 | `enrolled_count` |
|---|---|---|---|---|
| 报名 | 无记录 / CANCELLED | 开课前 | `capacity` 为 NULL，或 `enrolled_count < capacity` | +1 |
| 取消 | ENROLLED | 开课前 | — | −1 |
| 标记完成 | ENROLLED | 开课后（`now >= start_time`） | — | 不变（完成的人也占名额） |

状态不满足时返回 409 `INVALID_STATUS_TRANSITION`。如果是对 ENROLLED 或 COMPLETED 的记录再次报名，返回更明确的 `ALREADY_ENROLLED`。

### 5.3 时间规则

| 操作 | 规则 | 违反时 |
|---|---|---|
| 创建课程 | `start_time > now`，`end_time > start_time` | 400 `VALIDATION_ERROR` |
| 编辑课程 | 只要 `end_time > start_time`。已开课的课程不能再改 `start_time` / `end_time` / `capacity`，标题、描述等其他字段可以改 | 409 `COURSE_STARTED` |
| 编辑容量 | 新容量不能小于当前 `enrolled_count` | 400 `CAPACITY_BELOW_ENROLLED` |
| 报名 / 取消 | 只能在 `now < start_time` 时操作 | 409 `COURSE_STARTED` |
| 标记完成 | 只能在 `now >= start_time` 时操作 | 409 `COURSE_NOT_STARTED` |

课程阶段 `phase` 不存数据库，按当前时间计算：`UPCOMING`（开课前，可以报名）/ `ONGOING`（进行中）/ `ENDED`（已结束）。

### 5.4 时间与时区
- 全部用 `LocalDateTime` 存到 `DATETIME` 列，读写时 JDBC 不做时区换算。
- 业务里的「当前时间」只从注入的 `Clock` 取：`Clock.system(ZoneId.of(app.time-zone))`，默认 `Asia/Shanghai`。代码里不直接调用 `LocalDateTime.now()`。
  - 这样容器的默认时区（K8s 里一般是 UTC）不会影响「是否已开课」的判断，否则会差 8 小时。
  - 测试时可以换成 `Clock.fixed(...)`，用来验证「开课前 1 秒」「开课后 1 秒」这类边界。
- 接口里的时间格式是 ISO-8601 本地时间 `2026-11-10T09:00:00`，表示北京时间。

## 6. 并发控制（容量限制的核心）

**问题**：容量 30 的课，最后 1 个名额被 2 个人同时抢；或者同一个人连点两次报名。先查名额、再写入的做法在并发下会超卖。

**方案**：报名和取消时，先对课程这一行加悲观锁，让同一门课的写操作排队执行。

```java
@Transactional
public EnrollmentVO enroll(long courseId, long userId) {
    Course course = courseMapper.selectByIdForUpdate(courseId);     // SELECT ... FOR UPDATE
    if (course == null) throw COURSE_NOT_FOUND;
    if (!now().isBefore(course.getStartTime())) throw COURSE_STARTED;
    Enrollment e = enrollmentMapper.selectByCourseAndUser(courseId, userId);
    if (e != null && e.getStatus() != CANCELLED) throw ALREADY_ENROLLED;
    if (course.getCapacity() != null && course.getEnrolledCount() >= course.getCapacity()) throw COURSE_FULL;
    if (e == null) enrollmentMapper.insert(Enrollment.newEnrolled(courseId, userId, now()));
    else           enrollmentMapper.updateById(e.reEnroll(now()));
    courseMapper.incrementEnrolledCount(courseId, +1);
    ...
}
```

- 锁只针对单门课，不同课程之间互不影响；内部系统的并发量下吞吐足够。
- 取消、编辑容量也先加同一把锁，避免容量校验和报名同时进行时互相干扰。
- 唯一索引 `uk_enrollment_course_user` 作为最后一道防线。万一并发插入撞了唯一键，`DuplicateKeyException` 会被转成 409 `ALREADY_ENROLLED`，事务回滚，计数不会多加。
- 判断依据都在数据库里，不依赖 JVM 内的锁，所以后端多副本部署时依然正确。
- **验证**（`ConcurrencyIT`，每个场景用 `@RepeatedTest(3)` 跑 3 次，所有线程用 `CountDownLatch` 同时起跑，直接调用 Service 让竞争尽可能激烈）：
  - 20 个用户抢 5 个名额：恰好 5 个成功、15 个返回 `COURSE_FULL`，最终 `enrolled_count = 5`，有效报名记录也是 5 条
  - 同一用户 10 个线程同时报名：只有 1 个成功、9 个返回 `ALREADY_ENROLLED`，表里只有 1 条记录
  - 3 人取消的同时 12 人报名（容量 3）：结束后 `enrolled_count` 等于有效报名记录数，且不超过容量
- 管理员标记完成时，先按报名记录找到课程并加锁，**加锁后再重新读取一次报名记录**，防止和同时进行的取消操作冲突，基于加锁前读到的旧状态做判断。

## 7. API 设计

### 7.1 约定
- 前缀 `/api`，JSON 格式，认证头 `Authorization: Bearer <token>`。
- **成功**：直接返回资源，用 HTTP 状态码表达结果（200 / 201 / 204）。
- **失败**：统一返回 `{"code": "COURSE_FULL", "message": "课程名额已满", "details": {...}}`，由 `@RestControllerAdvice` 集中生成。
- **分页**：请求参数 `page`（从 1 开始）、`size`（默认 10，最大 100）；返回 `{"records": [...], "total": 42, "page": 1, "size": 10}`。

### 7.2 认证与用户

| 接口 | 权限 | 说明 |
|---|---|---|
| `POST /api/auth/register` | 公开 | 员工自己注册 → 201 用户信息 |
| `POST /api/auth/login` | 公开 | → `{token, expiresAt, user}` |
| `GET /api/auth/me` | 登录 | 当前用户信息 |
| `PUT /api/auth/password` | 登录 | 修改自己的密码 `{oldPassword, newPassword}` |
| `GET /api/users?keyword=&page=&size=` | ADMIN | 用户列表 |
| `POST /api/users` | ADMIN | 创建用户（可以选择角色） |
| `PATCH /api/users/{id}/enabled` | ADMIN | `{enabled: false}` 停用/启用 |
| `PUT /api/users/{id}/password` | ADMIN | 重置密码 `{newPassword}` |

### 7.3 课程

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/courses?keyword=&phase=&page=&size=` | 登录 | 每条附带 `enrolledCount`、`remaining`（不限人数时为 null）、`phase`、`myStatus`（当前用户在这门课的报名状态） |
| `GET /api/courses/{id}` | 登录 | 课程详情，字段同上 |
| `POST /api/courses` | ADMIN | 创建课程 |
| `PUT /api/courses/{id}` | ADMIN | 编辑课程，规则见 §5.3 |

- **列表默认排序**：未开始的课程排在前面，按开始时间升序（最近要开的排最前）；进行中和已结束的课程排在后面，按开始时间降序。按阶段筛选时也遵循这个顺序。`now` 由服务端从 Clock 取出后传给 SQL，不在 SQL 里用 `NOW()`。
- **创建和编辑共用请求体** `CourseRequest`：`capacity` 为 null 表示不限人数。时间精确到秒，服务端会截掉小数秒，避免「值没变却被判定为修改了时间」。
- **可置空的字段**（容量、地点、介绍）在 MyBatis-Plus 中使用 `FieldStrategy.ALWAYS`，否则 `updateById` 会跳过 null，「改为不限人数」就不会生效。

### 7.4 报名

| 接口 | 权限 | 说明 |
|---|---|---|
| `POST /api/courses/{id}/enrollments` | 登录 | 当前用户报名 → 201 |
| `DELETE /api/courses/{id}/enrollments/me` | 登录 | 当前用户取消报名 → 204 |
| `POST /api/courses/{id}/enrollments/me/complete` | 登录 | 本人标记学习完成 |
| `GET /api/courses/{id}/enrollments?status=&page=&size=` | ADMIN | 报名人员列表（连表带出姓名、部门、谁确认的完成） |
| `POST /api/enrollments/{enrollmentId}/complete` | ADMIN | 管理员给某条报名标记完成 |
| `GET /api/me/enrollments?status=&page=&size=` | 登录 | 我的报名（连表带出课程信息） |
| `GET /api/me/stats` | 登录 | 我的统计 `{enrolled, completed, cancelled}` |

- **返回值**：报名成功返回 201 和报名记录（`EnrollmentVO`），取消返回 204，标记完成返回 200 和更新后的记录。`completedBy` 等于 `userId` 时表示本人确认。
- **报错**：没有报名记录时取消或标记完成，返回 404 `ENROLLMENT_NOT_FOUND`；状态不允许时（比如重复取消、对已取消的记录标记完成），返回 409 `INVALID_STATUS_TRANSITION`。
- **重新报名**：取消后再报名，复用原来那条记录（id 不变），刷新报名时间、清空取消时间，名额检查和首次报名完全一样。
- **报名人员列表**：按报名时间倒序；额外带出 `completedByName`（确认人姓名）和 `selfConfirmed`（是否本人确认）。
- **我的报名**：按课程开始时间倒序；每条记录带有按当前时间计算出的课程阶段 `phase`，前端据此决定显示「取消」「标记完成」还是「重新报名」。
- **我的统计**：按状态分别计数。`enrolled` 只统计**当前处于已报名**的课程，不包含已完成的。

### 7.5 统计（ADMIN）

| 接口 | 返回内容 |
|---|---|
| `GET /api/stats/overview` | 课程总数、未开始/进行中/已结束各多少门、有效报名人次（ENROLLED + COMPLETED）、完成人次、整体完成率、参与员工数、用户总数 |
| `GET /api/stats/courses?sort=enrolled\|completionRate&limit=` | 按课程统计：报名数、完成数、完成率、名额占用率；默认按报名数取前 10 |

全部用 `GROUP BY` / `COUNT` 实时聚合（SQL 写在 `StatsMapper.xml`），数据量小，不做预计算。

### 7.6 错误码

| HTTP | code | 场景 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 参数校验失败（`details` 里给出具体字段） |
| 400 | `CAPACITY_BELOW_ENROLLED` | 容量改到比已报名人数还小 |
| 401 | `UNAUTHORIZED` | 没带 token、token 无效或过期、账号已停用 |
| 401 | `BAD_CREDENTIALS` | 用户名或密码错误 |
| 403 | `FORBIDDEN` | 角色不够 / 操作别人的报名 |
| 404 | `COURSE_NOT_FOUND` / `ENROLLMENT_NOT_FOUND` / `USER_NOT_FOUND` | 资源不存在 |
| 404 | `RESOURCE_NOT_FOUND` | 接口路径不存在 |
| 405 | `METHOD_NOT_ALLOWED` | 请求方法不支持 |
| 409 | `USERNAME_TAKEN` | 注册或建号时用户名重复 |
| 409 | `ALREADY_ENROLLED` | 重复报名 |
| 409 | `COURSE_FULL` | 名额已满 |
| 409 | `COURSE_STARTED` | 开课后报名、取消，或修改时间/容量 |
| 409 | `COURSE_NOT_STARTED` | 开课前标记完成 |
| 409 | `INVALID_STATUS_TRANSITION` | 状态不允许（例如已完成的报名不能取消） |
| 409 | `CANNOT_DISABLE_SELF` | 管理员停用自己 |
| 429 | `TOO_MANY_REQUESTS` | 登录或注册过于频繁（由 nginx 返回，§9.4） |
| 500 | `INTERNAL_ERROR` | 未预期的异常（只记录日志，不把内部信息返回给前端） |

## 8. 前端设计

### 8.1 路由

| 路由 | 页面 | 权限 |
|---|---|---|
| `/login`、`/register` | 登录、注册 | 公开 |
| `/courses` | 课程列表：搜索、按阶段筛选、分页；显示名额进度条，按钮根据阶段和我的状态显示「报名 / 取消 / 已满 / 标记完成」 | 登录 |
| `/courses/:id` | 课程详情；管理员在这里看报名人员，并能逐条标记完成 | 登录 |
| `/courses/new`、`/courses/:id/edit` | 课程表单；开课后时间和容量字段只读 | ADMIN |
| `/my/enrollments` | 我的报名：按状态分标签页、可以取消或标记完成，顶部显示个人统计 | 登录 |
| `/stats` | 统计：指标卡片 + 课程统计表 | ADMIN |
| `/admin/users` | 用户管理：列表、新建、停用/启用、重置密码 | ADMIN |
| `/account/password` | 修改密码 | 登录 |

### 8.2 技术细节
- **状态**：Pinia 的 `auth` store 保存 token 和当前用户，同步写入 localStorage（读写都包在 try/catch 里）。启动时如果有 token，就调一次 `/api/auth/me` 校验。
- **请求**：Axios 实例在请求头里加 Bearer token；收到 401 就清掉登录状态，跳到 `/login?redirect=...`；其他错误统一用 `ElMessage` 弹出后端返回的 `message`。
- **路由守卫**：通过 `meta.requiresAuth` / `meta.requiresAdmin` 控制访问；导航菜单也按角色显示。
- **类型**：后端的 DTO 在 `src/types/api.ts` 里写一份对应的 TypeScript 类型；每个业务模块一个 API 文件（`src/api/*.ts`）。
- **时间**：用 dayjs 格式化；后端返回的就是北京时间，前端不做时区换算。
- **开发联调**：Vite 的 dev server 把 `/api` 代理到 `localhost:8080`；生产环境由 nginx 代理。

## 9. 部署

### 9.1 Docker
- **后端**：`maven:3.9-eclipse-temurin-21` 构建（先单独下载依赖，利用构建缓存）→ `eclipse-temurin:21-jre` 运行，用非 root 用户，JVM 参数 `-XX:MaxRAMPercentage=75`。
- **前端**：`node:24-alpine` 构建 → `nginx:alpine` 运行。nginx 配置 SPA 回退（找不到的路径都返回 `index.html`），`/api` 反向代理到 `${BACKEND_URL}`。
- **docker-compose**：`mysql`（带 healthcheck 和数据卷）→ `backend`（等 MySQL 健康后再启动）→ `frontend`（宿主机端口 8000）。一条命令就能在本地跑起来。

docker-compose 只用于本地开发（暴露了 3306 端口、带默认密码），**不能用于服务器部署**。

### 9.2 生产环境

| 项 | 情况 |
|---|---|
| 服务器 | 火山引擎云服务器 1 台：Ubuntu 22.04，4 核 / 7.1 GiB / 约 44 GB 磁盘，x86_64（amd64），公网 IP `101.96.237.10` |
| 集群 | kubeadm 自建单节点 K8s v1.36.6；containerd 2.4.2（服务器上没有 Docker）；Calico 网络；local-path 本地存储（默认 StorageClass） |
| 网络限制 | 服务器直连 docker.io / GitHub 会超时，公共镜像通过 `m.daocloud.io/` 前缀拉取；云安全组默认只放行 SSH |
| 访问方式 | 不使用域名，直接访问 `http://101.96.237.10:30080` |

### 9.3 K8s 清单（`deploy/k8s/`，kustomize）

```
deploy/k8s/
├── base/                     与环境无关的通用清单
│   ├── namespace.yaml
│   ├── mysql.yaml            ConfigMap(my.cnf) + headless Service + StatefulSet
│   ├── backend.yaml          ConfigMap + Deployment ×2 + Service
│   ├── frontend.yaml         Deployment ×2 + NodePort Service
│   └── mysql-backup.yaml     备份卷 + 每日备份 CronJob
└── overlays/prod/            生产环境差异：MySQL 镜像地址、Secret、存储类
    ├── kustomization.yaml
    ├── storageclass-retain.yaml
    └── secret.env.example    首次发布时自动生成 secret.env（不进 Git）
```

| 资源 | 要点 |
|---|---|
| MySQL | StatefulSet ×1，镜像 `mysql:8.4.13`（通过 daocloud 拉取），数据卷 5Gi，`innodb_buffer_pool_size=256M`；只有集群内的 headless Service，不对外 |
| 存储类 | 新建 `local-path-retain`（回收策略 Retain）。默认的 local-path 是 Delete，误删 PVC 或命名空间时数据会一起被删；改成 Retain 后数据目录会保留 |
| backend | Deployment ×2；滚动发布 `maxUnavailable: 0`；先用 initContainer 等 MySQL 就绪；配置 startup/readiness/liveness 三种探针；preStop 先等 5 秒再停，配合 Spring 优雅停机；根文件系统只读，`/tmp` 用 emptyDir |
| frontend | Deployment ×2；NodePort 30080；`externalTrafficPolicy: Local`，保留用户的真实 IP（限流要用） |
| Secret | 由 `secretGenerator` 从 `secret.env` 生成，名字带内容哈希，改了密钥会自动触发滚动更新 |
| 资源上限 | MySQL 1Gi、backend 768Mi ×2、frontend 128Mi ×2，合计约 3Gi。控制平面已占约 1.3Gi，7.1Gi 内存够用 |

- 除 MySQL 外，所有容器都以非 root 运行，并关闭所有 Linux capabilities。MySQL 官方镜像的启动脚本需要先用 root 初始化数据目录，之后会自动切换到 mysql 用户。
- 所有 Pod 都设置 `enableServiceLinks: false`。K8s 默认会把 Service 地址注入成 `MYSQL_PORT` 这类环境变量，可能和 MySQL 镜像自己的变量冲突。
- Flyway 迁移时会加数据库锁，多个副本同时启动也只会有一个执行迁移。

### 9.4 对外访问与安全
- 云安全组只新增放行 **TCP 30080**；6443、3306 和其他 NodePort 都不开放。
- MySQL 和后端都只有集群内地址。外部只能经 nginx 访问 `/api`，`/actuator` 不对外；生产配置（`application-prod.yml`）关闭了 Swagger。
- nginx 按 IP 限制登录和注册请求：每分钟 30 次，允许突发 20 次。超出时返回 429 `TOO_MANY_REQUESTS`，响应体格式和后端错误一致。另外加了基础的安全响应头，并隐藏 nginx 版本号。
- **已知风险**：没有域名就没有 HTTPS，登录密码会以明文在网络上传输。目前只适合内部验收和演示。正式给全公司使用前，需要申请域名、完成 ICP 备案，再加上 HTTPS（入口控制器用 Traefik，证书用 cert-manager；ingress-nginx 已于 2026-03 停止维护）。

### 9.5 镜像与发布
- 镜像在开发机上用 Docker Desktop 构建（linux/amd64）。标签用 Git commit 号；如果工作区有未提交的改动，标签再加 `-dirty-时间戳`。不使用 `latest`，因为标签相同时，`IfNotPresent` 拉取策略会继续用节点上的旧镜像。
- 镜像送到服务器有两种方式，`deploy/deploy.ps1` 都支持：

| 方式 | 做法 | 适合 |
|---|---|---|
| A. 镜像仓库（推荐阿里云 ACR 个人版） | 推送到仓库，集群通过 imagePullSecret 拉取；回滚时直接用旧标签重新发布 | 常规做法，以后可以接 GitHub Actions 自动构建。ACR 个人版免费，但官方定位是开发测试、没有 SLA |
| B. 直接导入 | `docker save` 导出 → scp 上传 → 在服务器上用 `ctr -n k8s.io images import` 导入 | 不想注册镜像仓库；只适合单节点 |

- **发布流程**（一条命令完成）：构建镜像 → 推送或导入 → 本地用 kustomize 渲染清单 → scp 上传到服务器 → `kubectl apply` → 等待滚动更新完成 → 删除服务器上的渲染文件（里面含密钥）→ 通过公网地址做冒烟检查。
- **回滚**：`kubectl -n tcms rollout undo deployment/backend`；用方式 A 时也可以用旧标签重新发布。
- **数据库迁移只增不改**：只新增列和表，不删除、不改名。这样回滚到上一版代码时，旧代码仍能在新表结构上运行。

### 9.6 数据备份
- 每天 03:00（北京时间）由 CronJob 用 `mysqldump --single-transaction` 导出 tcms 库，gzip 压缩后存到单独的备份卷，保留 7 天。
- 备份卷和数据卷在同一块磁盘上，**磁盘损坏时会一起丢失**。所以还需要定期把备份下载到本地，并在火山引擎控制台给云盘开启自动快照。
- 操作步骤见 `docs/部署手册.md`。

## 11. 交付与协作

### 11.1 PR 拆分
`main` 分支只通过 PR 合入。每个 PR 都是**后端加对应前端页面**的完整功能，合并后可以在页面上直接使用。每个 PR 都有独立的实现文档（[docs/实现计划/](实现计划/README.md)），写明任务清单、测试、自测步骤和完成标准。

| PR | 分支 | 内容 |
|---|---|---|
| PR1 | `main` | 项目骨架、设计文档、Docker / K8s 清单（已完成） |
| PR2 | `feat/auth` | 注册、登录、JWT、用户管理 + 前端页面 + CI |
| PR3 | `feat/course` | 课程增改查、时间规则 + 课程列表、表单、详情页 |
| PR4 | `feat/enrollment` | 报名、取消、完成、我的报名、报名人员 + 容量限制和并发测试 |
| PR5 | `feat/stats` | 统计接口 + 统计页 |
| PR6 | `chore/delivery` | 自测说明、AI Coding 使用说明、前端按需引入、README 收尾 |

最初的方案是把前端页面集中在一个 PR 里，后来改成按功能切分：每个 PR 都能端到端验证，评审时的改动量也更小。CI 提前到 PR2，之后每个 PR 都会自动跑测试。
